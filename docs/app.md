# App 和通信方案

2026-11-02 定，2026-11-02 晚改了传输方式（见下）。这份是决定，不是选项：照这里做，改动之前先回来改这份。[plan-app.md](plan-app.md) 里的阶段 2、3 都以这里为准。

## 一句话

**先做 PWA，由宿主自己发，经 `fairy.lycoreco.cn` 的 HTTPS 入口访问，只暴露她自己的两条路径；第一版不做系统推送。**

## 传输：用现成的域名，只开她自己的入口

最初写的是 Tailscale 私有网络。主人说不想用 Tailscale——那就用他已有的东西：`lycoreco.cn` 的域名和 nginx。现在：

- `https://fairy.lycoreco.cn/fairy/app/` 是她的页面，手机浏览器直接打开，**不装任何客户端**；
- nginx 只反代三条路径：`/fairy/app`、`/fairy/link/v1`（WebSocket）、`/fairy/link/pair`；**其余一律 404**，DSH 的界面、`/api`、会话、她的生命文件都不出公网；
- 证书是 Let's Encrypt 的，`certbot.timer` 自动续期，续期后 reload nginx；
- 宿主本身仍然只监听 `127.0.0.1:3090`——公网上的东西只有 nginx。

### 为什么这样不危险（以及哪里仍然危险）

她的 agent 能在宿主上跑命令，所以"谁能连上她"约等于"谁能在那台机器上跑命令"。这条路打开的当天，服务器上同时加了 systemd 沙箱（`scripts/server/fairy.service.d/sandbox.conf`）：

- `/www`（博客源码、MySQL 数据、宝塔面板、nginx 配置）和 `/root` 在她的**挂载命名空间里不存在**。拿到设备令牌的人拿到的是一个看不到博客的 shell；
- 她以 `fairy` 用户运行，不是 root；`MemoryMax=768M`，跑飞了也拖不垮博客；
- 入口本身：HTTPS + 设备令牌（32 字节、只存哈希、可吊销），配对码一次性、5 分钟、同一个 IP 连错 5 次锁 5 分钟。

仍然危险的：**拿到令牌的人可以和她说话、让她在自己的家和 `workspace` 里动手**，而 `fairy-guard` 只在删除、对外发送、花钱、动凭据时问主人——普通的读文件、跑命令不问。所以令牌要当密码看待，别放进截图、别提交。

想回到"完全不暴露到公网"也可以：关掉那个 vhost 就行，代码一行不用改；Tailscale 那条路仍然可用，只是不是默认。

为什么不用 Tailscale 做默认：每台设备都要装、登录、加入 tailnet，主人明确说不想用。私有网络适合"更稳更低暴露"，公网入口适合"打开就能用"，这一版的取舍是后者。改主意就回来改这一节。

## 客户端：PWA 优先

形态：一个**宿主自己发的静态页面**，路由在 `/fairy/app/`（`ctx.webServer.register` 的 prefix 路由），单页、无框架、原生 DOM + 宿主发出来的 `protocol.js`。

代码放在 `packages/app/fairy-app`，不是 `apps/fairy-app`：页面和协议模块必须跟着一个**包**走，profile 只链接 `@fairy/bundle`，`apps/` 下的东西在运行时找不到。`web/` 里是页面和脚本，`src/index.ts` 只负责发这三个文件。

客户端**没有构建步骤**：`web/app.js` 是手写的 ESM，唯一的共享代码是宿主在 `/fairy/app/protocol.js` 发出来的 `@fairy/protocol` 编译产物（它没有 import，浏览器能直接跑）。加一个 bundler 就多一条会坏的构建链，不值当。

理由：

1. **零分发**。装 Tailscale 就能用，不用过应用商店、不用签名、不用等审核。
2. **改起来快**。她的话术、确认卡片的样子，改一次宿主重启就生效，没有版本碎片。
3. **协议已经现成**。`@fairy/protocol` 里的帧和校验是给任意客户端用的，PWA 只是又一个客户端。
4. **可替换**。以后真要做原生（Tauri / Flutter），协议和宿主一行不用改，换的只是那层壳。

不做的：不引 React/Vue 之类框架，不做离线缓存她的生活（她的数据只存在宿主），不做多用户。

页面和 `/fairy/link/pair` 都不经过 DSH 的网页 token，它们自己用设备令牌认证；和 DSH 的路由一样只监听本机地址，跨端靠 Tailscale（见下）。

### 里程碑

| 步骤 | 做什么 | 验收 |
|---|---|---|
| M1 ✅ | 静态页面 + 配对 + 聊天（`say` → `reply.done`） | 2026-11-02 在真宿主上验过：浏览器里配对 → 说话 → 她回；刷新页面令牌还在、自动重连；她的话进了生命 |
| M2 部分 ✅ | 历史记录 + 图片 + 文本文件 | 2026-11-02 验过：打开页面就看到之前的全部对话（来自她的生命日志，搬家前说的也在）；从相册选图 → 客户端缩到 1280 长边、JPEG 0.72 → 她收到并描述得出图里是什么；选一个 `.md` → 她读到全文并照内容回话 |
| M2 ✅ | 确认卡片 + 她的状态 | 卡片带按钮，点了就回；她的状态（醒着/在做什么/精力）在标题栏 |
| M3 部分 ✅ | 她主动找来时，页面关着也会响：Web Push（Service Worker + VAPID），手机上点一次"开启通知"即可 | 页面开着走 WebSocket，关着走系统通知；通知里只放一句提示，不放进正文（决策 25） |
| M3 剩余 | 会话切换（`sessions`）+ 断线重连补上漏掉的回复 | 关掉页面，她主动说话后重开能看到；断网 30 秒后恢复不丢消息 |

M1–M3 全在这个仓库里，宿主自带，没有第二个要发布的产物。

## 推送：第一版只做"页面活着时收到"

- 她的主动发言（`urge`）已经在协议里；M3 完成后，页面开着（或后台保活）就能收到。
- 系统级推送**先不做**：国内 Android 没有可靠 FCM，要接厂商通道或聚合服务（极光、个推），iOS 走 APNs——那是一笔长期维护债，而且推送内容会经过第三方。等 PWA 真的用起来、确实觉得"页面关着也想被找到"再做，届时推送里只放"Fairy 有话对你说"，正文等 App 连上宿主再取。
- 宿主侧不需要为推送改任何东西：她的话照常进会话（决策 16），推送只是送达方式。

## 设备节点（阶段 4）：等她真需要动手时再说

`fairy-node` 是另一件事：跑在主人的 PC/NAS 上、只执行、本地也有黑名单。它的前提是 App 已经能用、并且真的出现"她在网页里够不到那台机器"的场景。技术方案在 [plan-app.md](plan-app.md) 阶段 4，不变。

## 这个方案怎么保持可持续

- **协议是合同**：`@fairy/protocol` 有版本号，两端校验；加字段不算破坏性变更（校验只拒绝不认识的**类型**，不拒绝多余字段），删字段或改语义才加版本。
- **App 是独立目录**：`apps/fairy-app`，坏了不影响她活着；宿主不认识 App 的任何实现，只知道协议。
- **不用为 App 改内核**：App 需要的新能力先进 `FairySelf` 接缝，再由 `@fairy/isla` 实现；App 只调协议。
- **测试在协议层和设备层**：帧的校验、配对的失效、确认的"没人答就拒绝"，都有测试；PWA 自己的 UI 用 M1–M3 的验收代替（手工一遍，记录在本文）。

# App 和通信方案

2026-11-02 定。这份是决定，不是选项：照这里做，改动之前先回来改这份。[plan-app.md](plan-app.md) 里的阶段 2、3 都以这里为准。

## 一句话

**先做 PWA，由宿主自己发，只经私有网络（Tailscale）访问，第一版不做系统推送。**

## 传输：Tailscale，不上公网

- 宿主仍然只监听 `127.0.0.1:3090`。对外是 `tailscale serve` 把那个端口反代到私有网络里，Tailscale 自己管身份和加密。
- 不买域名、不开公网端口、不做端口映射。要公网访问是以后的事，届时必须先补：HTTPS（DSH 自带 `--tls-cert/--tls-key`）、配对限速（已有）、按 IP 的失败锁定（已有）、再加一层反代层的限流。
- 手机、平板、电脑装 Tailscale，登录同一个 tailnet，就能打开同一个她。**设备只是窗口，不复制她**。

为什么不是公网直接开：一个宿主就是她的全部，暴露到公网等于把家门的钥匙挂在门上；私有网络已经能覆盖"我在外面也能找到她"的全部真实需求。

## 客户端：PWA 优先

形态：一个**宿主自己发的静态页面**，路由在 `/fairy/app/`（`ctx.webServer.register` 的 prefix 路由），单页、无框架、原生 DOM + 宿主发出来的 `protocol.js`。

代码放在 `packages/app/fairy-app`，不是 `apps/fairy-app`：页面和协议模块必须跟着一个**包**走，profile 只链接 `@fairy/bundle`，`apps/` 下的东西在运行时找不到。`web/` 里是页面和脚本，`src/index.ts` 只负责发这三个文件。

客户端**没有构建步骤**：`web/app.js` 是手写的 ESM，唯一的共享代码是宿主在 `/fairy/app/protocol.js` 发出来的 `@fairy/protocol` 编译产物（它没有 import，浏览器能直接跑）。加一个 bundler 就多一条会坏的构建链，不值当。

理由：

1. **零分发**。装 Tailscale 就能用，不用过应用商店、不用签名、不用等审核。
2. **改起来快**。她的话术、确认卡片的样子，改一次宿主重启就生效，没有版本碎片。
3. **协议已经现成**。`@fairy/protocol` 里的帧和校验是给任意客户端用的，PWA 只是又一个客户端。
4. **可替换**。以后真要做原生（Tauri / Flutter），协议和宿主一行不用改，换的只是那层壳。

不做的：不引 React/Vue 之类框架，不做离线缓存她的生活（她的数据只存在宿主），不做多用户。

页面和 `/fairy/link/pair` 都不经过 DSH 的网页 token，它们自己用设备令牌认证；和 DSH 的路由一样只监听本机地址，跨端靠 Tailscale（见下）。

### 里程碑

| 步骤 | 做什么 | 验收 |
|---|---|---|
| M1 ✅ | 静态页面 + 配对 + 聊天（`say` → `reply.done`） | 2026-11-02 在真宿主上验过：浏览器里配对 → 说话 → 她回；刷新页面令牌还在、自动重连；她的话进了生命 |
| M2 | 确认卡片（`confirm` / `answer`）+ 她的状态（`status`） | 让她删一个临时文件，卡片在手机上弹出，点"不允许"她如实回报 |
| M3 | 会话切换（`sessions`）+ 她主动找来（`urge`）+ 断线重连补上漏掉的回复 | 关掉页面，她主动说话后重开能看到；断网 30 秒后恢复不丢消息 |
| M4 | 系统推送（可选，另行决定） | —— |

M1–M3 全在这个仓库里，宿主自带，没有第二个要发布的产物。

## 推送：第一版只做"页面活着时收到"

- 她的主动发言（`urge`）已经在协议里；M3 完成后，页面开着（或后台保活）就能收到。
- 系统级推送**先不做**：国内 Android 没有可靠 FCM，要接厂商通道或聚合服务（极光、个推），iOS 走 APNs——那是一笔长期维护债，而且推送内容会经过第三方。等 PWA 真的用起来、确实觉得"页面关着也想被找到"再做，届时推送里只放"Fairy 有话对你说"，正文等 App 连上宿主再取。
- 宿主侧不需要为推送改任何东西：她的话照常进会话（决策 16），推送只是送达方式。

## 设备节点（阶段 4）：等她真需要动手时再说

`fairy-node` 是另一件事：跑在主人的 PC/NAS 上、只执行、本地也有黑名单。它的前提是 App 已经能用、并且真的出现"她在网页里够不到那台机器"的场景。技术方案在 [plan-app.md](plan-app.md) 阶段 4，不变。

## 这个方案怎么保持可持续

- **协议是合同**：`@fairy/protocol` 有版本号，两端校验；加字段不算破坏性变更（校验只拒绝不认识的**类型**，不拒绝多余字段），删字段或改语义才加版本。
- **App 是独立目录**：`apps/fairy-app`，坏了不影响她活着；宿主不认识 App 的任何实现，只知道协议。
- **不用为 App 改内核**：App 需要的新能力先进 `FairySelf` 接缝，再由 `@fairy/isla` 实现；App 只调协议。
- **测试在协议层和设备层**：帧的校验、配对的失效、确认的"没人答就拒绝"，都有测试；PWA 自己的 UI 用 M1–M3 的验收代替（手工一遍，记录在本文）。

# 架构决策

每条写清楚选了什么、为什么。推翻一条之前，先在这里改。

## 1. 在 DSH 之上做插件，不 fork

Fairy 是一组 DeepSeek Harness（DSH）插件加一个 bundle，DSH 本身不改。DSH 的 agent loop、工具、会话、提示词组装都是可替换的插件，需要的改动都能通过加插件、挂事件、替换插件做到。DSH 还在预览期，官方明确说会有破坏性更新；fork 之后每次更新都要手工合并。

魔改的手段按侵入程度从低到高：改配置 → 加插件 → 挂事件 → 替换插件 → `pnpm patch`。最后一种必须在本文件写明原因。

## 2. 版本钉死

`@deepseek-ai/dsh` 和各插件的 `engines.dsh` 都钉在 `0.2.1-rc.5`。升级 DSH 就是：改版本号 → `pnpm install` → `pnpm test` → `pnpm smoke`。

## 3. Isla 是她的本体，DSH 是她的身体

她是谁（气质、情绪、精力、经历、对自己的认识）来自 `D:\isla` 的 `@isla/life`：一份只追加的生命日志，状态由日志算出来，每句关于自己的话都能追溯到事件。DSH 提供能做什么（对话、工具、会话、界面）。

- 只有 `@fairy/isla` import `@isla/*`。Isla 的 API 变了，只改这一个包。
- 只依赖 `@isla/life`，不碰正在退役的 `@isla/core` runtime。
- 依赖用 `link:` 指向 `D:\isla\packages\life`，两边同时开发。改了 Isla 之后要在 `D:\isla` 里重新 build。

## 4. 一个本体，多个窗口

她的生命在宿主层只开一次（`fairy-self` 行），每个会话只是一个窗口（`fairy-presence` 挂在 Fairy preset 里，每个会话一份）。将来的跨端部署也是这样：各端都连同一个宿主，不复制她。

生命日志只能有一个写入者，`fairy.life.jsonl.lock` 负责保证：第二个宿主打开同一份生命会直接报错。迁移就是搬走这个文件。

## 5. 身份放 system prompt，状态放动态上下文

名字、来历、说话方式在一条生命里不变，放进 system prompt，保持 KV 缓存稳定。心情、精力、正在做什么每轮都变，走 DSH 的动态上下文，每次请求前刷新。

## 6. 和用户原有的 DSH 完全隔离

- DSH 装在项目的 `node_modules`，不用全局安装，不碰桌面版。
- 启动脚本只给子进程设置 `DSH_HOME`、`DSH_AGENTS_HOME`，不改系统环境变量。
- 端口默认 3090，不用 DSH 默认的 3080。
- 首次使用时的默认工作区在她自己的 home 里，不在系统的“文档”文件夹。
- 凭据各管各的，不读 `~/.dsh`。

## 7. 隐私默认关闭上报

不随模型请求上传会话日志（`session-log-deepseek` 关闭），不发 OpenTelemetry 反馈（`DSH_TELEMETRY_MODE=DISABLED`）。两项都可以在 Web 设置或环境变量里重新打开。

## 8. 路径必须是 ASCII

在这台 Windows 上，pnpm 在中文路径下安装会 `EPERM` 失败，同样的安装放到英文路径就成功。所以项目放在 `D:\fairy-framework`，启动脚本拒绝非 ASCII 的 DSH home。

## 9. 对话进入她的生命

缺的接口补在 Isla 里，不在 Fairy 里绕：

- `listen()`：主人的话在模型被调用之前记成 `heard`（挂在 DSH 的 `agent/pre-step` 上，等它写完再发请求），所以这一轮的动态上下文已经反映她被叫醒、被勾起的记忆。她自己的心智不回话，不和 DSH agent 抢话。
- `speak()`：一轮结束（`session/event` 的 `turn/end`）时，把这一轮 assistant 的文字记成 `said`，`external: true`，不占她的心智预算。超过 2000 字只记开头，全文在 DSH 会话里。一轮什么都没说出来（比如模型出错），就不记，那句话保持没人回答。
- 睡着时被叫，会醒来，越累越有起床气。管家随叫随到，被叫醒这件事也是她的经历。
- 危机消息：Isla 给出固定回复，`fairy-presence` 要求模型在这一轮第一段一字不差地说出来。
- 只记人打的字（`source.kind === 'user'`），DSH 注入的上下文（文件变化、技能内容、定时提醒）不算她听到的话。
- 写生命日志失败只记警告，不拦对话。宁可漏记一句，不能让她不回话。

- 每句话记下它在哪个 DSH 会话里（`heard.where = dsh-session:<id>`）。她的生命只记说了什么；读过的文件、跑过的命令、工具输出留在 DSH 会话里，`fairy_recall` 的结果会带上这个指针。

外部感知用 `ctx.fairySelf.perceive()`：`World` 必须是时间的纯函数，外面的事只能作为日志事件进入。接口已经有了，但还没有任何感官在用它；给她哪些感官、要什么同意，由主人决定。

## 10. 记忆是日志的视图

见 [memory.md](memory.md)。记忆不是第二份数据，是 Isla 日志上的索引，删掉可以重建；检索和遗忘不调用模型。Fairy 的 genome 里 `memory: { decay: 0.4, records: ['heard', 'said'] }`：比人忘得慢，和主人说过的话主动查时永远原样可查。

每轮自然想起的几条进动态上下文，主动回想用 `fairy_recall` 工具，记下主人的事用 `fairy_note`（只能引用主人这一轮说的话）。还没办的事是 `pending` 的记录，常驻在她的事实里；到点提醒交给 DSH 的定时任务，不在她的生命里另做一套调度。DSH 的回复还没有标出用了哪些事实，所以对话里的引用暂时不算“用到”这段记忆；只有 `fairy_recall` 找到的会被加强。要标出引用，得先能在显示前处理最终回复。

## 11. 动手之前问主人，和 DSH 的审批无关

`fairy-guard` 挂在 `tools/pre-execute` 上，每次工具调用都过一遍规则：删除和不可撤销的操作、向外发送、花钱和动凭据，必须先在问题卡片上得到主人点头，不管 DSH 的审批策略是不是“从不询问”、沙箱是不是完全权限。主人在 2026-11-01 选了这三类；在工作区外写文件不用问。

- 主人说不行，她收到的是“不要换个写法再试”。没人能回答时一律不做。
- 每次调用都记进 `.fairy-home/audit.jsonl`：做了什么、为什么要问、主人怎么说、结果如何。
- 规则不读她的心情。
- 这是给诚实的失误加的一道网，不是沙箱：一条存心绕过的命令总能换个写法。

## 12. 她自己的日子

她窗外是主人那座城市真实的天：`fairy-senses` 每 30 分钟和每次她醒来时从 wttr.in 读一次，天变了她才会注意到；没配城市时她就没有天气，不会编一个。（2026-11-02 之前用的是 Isla 示例房间按种子编的天，她把它当成都的天说了出去，所以换掉。）

书架换成主人选的两样消遣：看新闻（`news` 书架，来自主人列的 RSS / Atom 订阅）和翻主人的项目（`projects` 书架，只用 `git log` 读主人列的仓库）。来源由 `fairy-senses` 放进书架，她什么时候去看、挑哪篇、喜不喜欢，都是她自己的：按她已经形成的口味挑，喜不喜欢某个话题由种子里的天生亲和决定，她要活了才知道。没列来源时，书架是空的，她就做别的。

## 13. 她会主动找主人

主人说“只要她想发，有事就可以发”，所以不设每日上限和免打扰时段。她想开口必须有生活里的理由：还欠主人一件事、刚看到主人会在意的东西、好久没说话了。主人正在和她说话时不发，睡着时不发，上一条没得到回复前不再发。

想开口是 Isla 的 `urged` 事件；`fairy-presence` 把它作为一轮她自己开始的对话，送进主人最近用的那个会话（不是主人打的字，模型看得到这一点）。她觉得不该打扰可以只回“…”，这不算说过话。没有打开的会话时，见 [16](#16-网页关着时她的话也能落进上次那个会话)。

## 14. 聊天的样子和她的性格分开

她的性格和说话方式写在 genome 里，出生后不能改。她聊天时说多长、用不用标题表格，是部署的事，放在 `fairy-presence` 的 `chatStyle`，主人可以在 profile 里改。默认是“像发消息一样”：一到三句话，先说结果，不用标题和表格，要细节再展开。用同一个模型、同样四个问题对比，回复从平均 196 字降到 73 字，标题和加粗从 2 处降到 0。

## 15. 关系随相处变化，只会变深

Isla 给每个人记着：哪几天来聊过、通常几点来、她和这个人现在是什么关系（初识 → 熟悉 → 亲近 → 信赖）。关系要靠“很多天都聊、而且她喜欢和你聊”才会变深，一个晚上聊再多也不算；按主人的选择，关系不会变淡，长时间不聊也不会被记仇。每往前一步，是一条 `bonded` 事件，写明原因，她以后也想得起来。

口气怎么跟着变是部署的事，放在 `fairy-presence` 的 `bondTones`：初识时公事公办、带点距离；熟悉了会顺口损两句；亲近了关心藏不住；信赖时说话放松、敢说主人不爱听的话。不管哪一步，她都还是她。这一行放在每次请求的动态上下文里，不进缓存的 system prompt。

## 16. 网页关着时，她的话也能落进上次那个会话

她想说话时，先找当前开着的会话。一个都没有（网页关了、DSH 上没有会话在跑）时，从她的生命里取最近一条 `heard.where`（`dsh-session:<id>`），用 `ctx.get('sessionController').resolveAgent()` 把那个会话唤醒，再把这一轮当作“她自己开始的对话”送进去。这和 DSH 自己的定时提醒投递方式一样（`@deepseek-ai/dsh-schedule` 就是这么做的）。

- `where` 从日志里读（`FairySelf.lastConversation()`），所以宿主重启以后还在；比它更新的 `perceived`、`stocked` 这类没有 `where` 的事件不会把它盖掉。
- 没有会话可唤醒、宿主上没有 `sessionController`、或那个会话已经不在了：这一次不发，只记一条日志。不假装送达，也不写进 `speakUp`——她的话只有真的被说出来才算说过。
- 为什么不用 DSH 的定时任务代发：她的话必须是“她的一轮”被模型说出来，再被 `speakUp` 记进生命；定时任务不产生她的 `urge`，也不经过她的口气。
- 手机推送（[plan-app](plan-app.md) 阶段 1 的 `@fairy/link`）接上以后，这一段负责“话已经落进会话”，推送只是送达方式。

## 17. 通道：手写 WebSocket，令牌只存哈希，确认先问设备

- **WebSocket 手写**（`packages/link/fairy-link/src/socket.ts`）：握手、文本帧、分片重组、ping/close，服务端和 CLI 共用。理由是 `ws` 的 TypeScript 类型包不在离线依赖里，而这条线只走短 JSON，用不上一整套库。没有分片以外的扩展：不发二进制，不压缩。
- **令牌只存哈希**：32 字节随机令牌交给设备，`devices.json` 里只留 SHA-256。备份文件被读走也换不成设备；吊销就是删一行，立刻失效。
- **配对码同时只有一个**：6 位、5 分钟、用一次作废、重发就作废旧的（两个活码等于把猜中的概率翻倍），同一个地址连错 5 次锁 5 分钟。配对只在她监听的本机地址上提供。
  - 2026-11-02 加了一条：码**每 5 分钟自动换**，最新的一直写在 `.fairy-home/pairing-code`（0600），`node scripts/fairy.mjs pair` 打出来；配对成功立刻换新的。原因很实际——只在启动时印一次，意味着"错过就得重启她"，而她现在在一台没人看着的服务器上。
- **设备先接在 DSH 自己的 Web 服务器上**（`ctx.webServer.register` / `registerUpgrade`），不另开端口、不自己管 TLS。跨端开放之前要先做阶段 0：TLS + 私有网络。
- **确认先问设备，再问 Web UI**：这一步在 `fairy-guard` 里，因为 guard 是宿主级插件、手里就有这次调用的上下文，不需要碰那个 Agent 作用域的 waterfall。顺序是：`ctx.get('fairyLink')?.confirm()` → 设备答了就用它；没有设备 / 设备超时 → `ctx.userQuestions.ask()` 交 Web UI；Web UI 120 秒还没人答 → 拒绝（`askTimeoutMs`）。
  - 为什么要这么绕：`user-questions/request` 用 `scopeTarget(agent, agent)` 派发，实测（2026-11-02）在没人开浏览器时这个 waterfall 能一直不返回——回合永远不结束，比拒绝更糟。原来把监听放在 `@fairy/link`（宿主级）根本收不到，放在 `fairy-presence`（Agent 作用域）才收得到，但排在客户端转发之后，依旧被挡住。绕开它的唯一稳的办法是让 guard 直接问设备。
  - 设备上的卡片在 Web 回答后不会自动收起——协议还没有撤回帧。
- **DSH 自己的审批被让开**：bundle 里加了 `fairy` 权限预设（`sandbox: workspace-write` + `approval: never`）并设为默认。`never` 的意思是"需要审批的动作直接拒绝"，不是放行；这样没人看着时不会卡住，guard 成为唯一的人闸，且它答不上来时一律拒绝。
- **她的话落进哪个会话**：设备点名了就用那个；否则用它已经接上的；否则用她最近说话的那个（决策 16 的 `lastConversation()`）；一个都没有才新开一个。全程不猜：开不出来就是设备的错误帧。

## 18. 跨端第一步：PWA + Tailscale，不上公网

客户端先做成**宿主自己发的静态页面**（`/fairy/app/`，无框架），经 **Tailscale 私有网络**访问，宿主仍然只听 `127.0.0.1`。第一版不做系统推送。完整方案和里程碑在 [app.md](app.md)。

- 为什么不先做原生：一个聊天框加一个确认卡片，不值当一套 Flutter/RN 的构建链和分发；PWA 装 Tailscale 就能用，改一次重启就生效。
- 为什么不上公网：宿主就是她的全部，开公网口等于把钥匙挂在门上；私有网络已经覆盖真实需求。要公网时先补 HTTPS 和反代限流，那些写进 app.md。
- 为什么不改宿主：App 只是又一个协议客户端。它需要的新能力先进 `FairySelf` 接缝，再由 `@fairy/isla` 实现。

## 19. 能长期活下去靠三样：可读的健康、可逆的升级、不动的底线

- **可读的健康**：`pnpm doctor`（`healthReport`）一次回答"她还好吗"——生命能不能读、谁在写、备份新不新、语义回想开没开、网页答不答。只读，不加锁，随时能跑。
- **可逆的升级**：DSH 版本钉死（决策 2），升级是一套固定动作（改版本 → 装 → 测试 → 冒烟 → 手工验一次通道），不是随手 `pnpm update`；生命内核在另一个仓库、单独分支、单独测试。步骤写在 [maintenance.md](maintenance.md)。
- **不动的底线**：她的生命只追加、只备份、不编辑；一个宿主一个写入者；任何"修"之前先复制。这三条比任何功能都重要，写进 AGENTS.md 和 maintenance.md。
- 出问题的顺序永远是先看 `doctor`，再查锁、端口、日志，最后才谈备份恢复。

## 20. 公网入口只开她自己的三条路径，并且给她加沙箱

2026-11-02 晚推翻了决策 18 里的"不上公网"：主人不想用 Tailscale，要求"打开就能用"。改成 `https://fairy.lycoreco.cn`——用他已有的域名和 nginx，证书 Let's Encrypt 自动续。

- **只反代三条路径**：`/fairy/app`、`/fairy/link/v1`、`/fairy/link/pair`。nginx 里其余一律 404；DSH 的界面、`/api`、会话、她的生命文件仍然只在 `127.0.0.1:3090` 上。宿主本身没变——它从来没有监听公网地址。
- **同时给她加 systemd 沙箱**：她能跑 shell，所以"谁能连上她"约等于"谁能在那台机器上跑命令"。`InaccessiblePaths=/www`（博客源码、MySQL 数据、宝塔面板、nginx 配置）和 `/root` 在她的命名空间里不存在，`ProtectSystem=strict` + `ReadWritePaths=/home/fairy` 让其余文件系统只读。实测：从她进程的 `/proc/<pid>/root/www` 读博客源码是 `No such file or directory`。
- **仍然承认风险**：拿到设备令牌的人能和她说、让她在自己家里动手；guard 只在删除/对外发送/花钱/凭据时问。所以令牌当密码看待。
- **可逆**：把那个 vhost 一删就回到"完全不暴露"；代码一行不用改。Tailscale 那条路还在，只是不是默认。
- 踩过的坑记在这里：`InaccessiblePaths` 里的路径必须**存在**，否则 systemd 直接 `status=226/NAMESPACE` 拒绝启动（`/etc/nginx`、`/var/lib/mysql` 在这台机器上都不存在，全在 `/www` 下）。
